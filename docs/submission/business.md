# Commercial feasibility — initial hypothesis

The first customers to explore are laboratory leads and course instructors with repeated, non-sensitive batch workloads and existing team devices. Start with a small supervised pilot: establish consent, verify campus connectivity, run matched workloads, and ask whether the saved waiting time justifies operating the pool. No interviews, paying customers, willingness-to-pay evidence, or validated demand are claimed here.

Alternatives are one person's laptop, a shared lab workstation, existing institutional clusters, and cloud compute. Compare the same workload, quality threshold, resource settings, user time and data-transfer cost. Current cloud prices must be verified immediately before any pitch; no unverified price is quoted.

The initial revenue hypothesis is a subscription for private-pool management, observability and administration. Participants join through existing lab/course relationships and retain control of offered capacity. Internal credits may support reciprocity, but do not imply cash earnings or a power marketplace.

Cost per accepted unit = (incremental energy + coordinator/storage + network + participant compensation + LLM + operations) / unique accepted units. Until measured, energy and operator time are estimates with explicit assumptions. Fixed-cost allocation, utilization, failed/repeated computation and AI planning must all be disclosed. With zero accepted units, unit cost is undefined.

Main adoption barriers are trust in other device owners, runtime installation, heterogeneous CPU/CUDA environments, battery/thermal impact, Wi-Fi client isolation and support burden. A single GPU remains a bottleneck; pooling does not merge VRAM. A pilot should test task completion time, contribution retention, operational effort and repeat usage. Continue commercially only if actual benefit exceeds these costs and participants want to keep using it.
