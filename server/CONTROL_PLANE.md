# Анализ control plane

## Объём и модель отказов

Часть 3 владеет API, серверными транзакциями, протоколом адаптеров и размещением координатора. Runner владеет обнаружением оборудования, sandbox и watchdog. Portal и Console владеют отображением. Публичный путь начинается с авторизованной сессии и заканчивается проверенным результатом и доступным артефактом. Для доказательства пула официальный бриф требует полезного вклада как минимум двух физических устройств в одной серии и сопоставимого standalone baseline. Серверные unit/integration tests проверяют семантику API и не служат исходными измерениями для этого доказательства.

| Граница | Решение | Что проверять при отказе |
|---|---|---|
| Клиент → API | UUID, отдельные роли и credentials, одноразовые приглашения, CSRF для browser mutation, SHA-256 и scoped access | Истёкшее приглашение, смена сессии, попытка доступа к чужому результату |
| Claim → попытка | Состояние задачи и общий ресурсный бюджет изменяются в одной транзакции PostgreSQL. Время берётся из БД, generation и token привязаны к сессии | Два конкурентных запроса на одну задачу, просроченный lease до reaper, повторный join |
| Compute → verification | Complete закрывает вычислительную аренду. Хеш payload и квитанция остаются в попытке. У валидатора отдельный claim и deadline | Потеря ACK, дубль с другим телом, падение координатора в verifying, гонка с отменой |
| Файл → ссылка | Часть и объект публикуются после сверки SHA-256 и fsync. Транзакция регистрирует только доступный blob. Orphan GC выдерживает grace period | Незавершённые части, расхождение checksum, ошибка записи, процесс между публикацией и commit |
| Verification → ledger | Acceptance и ledger имеют уникальный ключ задачи. Событие и итог фиксируются с ними. Частичный результат сохраняет уже принятые единицы | Поздний валидатор после отмены, повторная попытка, неуспех нижестоящего этапа |
| Planner → JobPlan | Асинхронная ревизия, разрешённые выдержки, подготовленный каталог, граф зависимостей, пути sandbox, digest входа, ресурсный профиль и правила resume | Структурно корректный вредный план, неподдерживаемый CUDA, неверная ревизия, timeout или refusal |
| PostgreSQL и storage → backup | Согласованный снимок с короткой остановкой API, отдельные volumes для проверки restore, сверка после восстановления | Недоступность исходного диска, checksum снимка, обнаружение отсутствующего blob |
| Worker → benchmark | Отдельные серии standalone, single-node-through-service и pool. У каждой сопоставимой серии одинаковый manifest и runtime. Сервер считает уникальные acceptance и фактических участников | Недостающий baseline, иной образ/лимит/режим, участник без результата, попытка задвоить измерение |

Короткие мутации координирует PostgreSQL advisory transaction lock. Это упрощает проверку порядка commit у cancellation, lease, событий и публикации. Сетевой запрос к LLM, получение тела загрузки, файловая сборка и вызов валидатора выполняются вне блокировки. Ресурсная совместимость предшествует выбору по владельцу. Очередь выбирает владельца, который дольше не получал совместимую работу. Порог допустимой нагрузки и цена глобальной сериализации требуют замера на реальном пуле. Переход к более мелким блокировкам имеет смысл после такого замера и требует сохранить порядок событий.

На сервере нет общего доверия к результатам произвольного кода. Structural policy подтверждает формат результата, объявленные пути и checksum. Formal benchmark принимает только full validation, а достоверность семантической проверки зависит от зарегистрированного адаптера. Standalone timings поступают с credential устройства. Отчёт отмечает источник worker telemetry и исключает из формулы серии, где фактический состав устройств или профиль расходится с baseline.

## Состояние приёмки

| Требование из плана | Доказательство или оставшаяся проверка |
|---|---|
| Foundation | OpenAPI, десять JSON Schema, fixtures для семи сценариев, mock API, генерация Go/TS/Python и CI. Рабочая ветка опубликована в GitHub |
| Сквозной путь | Smoke с живым FastAPI, PostgreSQL, доверенным HTTPS, реальным Docker и независимым валидатором SHA-256. Демонстрирует один физический ноутбук |
| Повторы и восстановление | PostgreSQL integration tests проверяют выдачу, expiry до reaper, rotation, lost ACK, cancellation, DAG и checkpoint. Restore проверен в отдельном Compose project с восстановленным артефактом |
| LLM | Провайдер и контроль ревизий реализованы. Проверки timeout, selected excerpts и semantic rejection выполнены с контролируемым провайдером. Для проверки внешнего endpoint нужны одобренная модель и credential |
| Интеграция portal/console | Production bundles собираются. У provisional UI есть расхождения с контрактом, включая `invitation`/ `token`, upload SHA-256, preview, сведения об узлах и benchmark. Требуется подключить DTO на стороне клиентов и пройти браузерный маршрут |
| Интеграция Go/ML | Скомпилированы Go DTO. Для двухустройственного embeddings, CUDA training, настоящего resume и измерений нужны runner, зарегистрированные workload-адаптеры и физические устройства |
| Методика брифа | Использовать новые данные, одинаковые quality/runtime/batching, минимум три повтора, раскрыть роли координатора и validator, сохранить raw observations, посчитать медианы, эффективность и speedup только для сопоставимых серий |

## Проверки площадки

На каждом разрешённом ноутбуке записать ОС, arch, CPU/RAM, CUDA/VRAM, Docker и его роль. С целевого SSID проверить доверенный TLS, handshake протокола, загрузку/скачивание и reconnect при переключении сети. Отдельно проверить Qwen из сети координатора, доставку обеих UI-сборок, собственный код с файлом модели и поисковый индекс на двух вычислителях. Для сбоя CPU подтвердить новую generation и отсутствие двойного acceptance. Для сбоя GPU подтвердить `waiting_for_capacity` и возобновление с последнего полного checkpoint после возвращения совместимого устройства. Сырые показатели и SHA интеграционного коммита передаются в отчёт панели.
